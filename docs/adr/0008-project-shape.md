# ADR-0008: 工程形态与代理模型

- 状态：已接受
- 日期：2026-11-16

## 背景

确定代码组织方式和单个 frpc 的代理容量。

## 决策

- **TypeScript + pnpm monorepo**：`packages/shared` 放协议/帧/类型定义，两端共用；`packages/frps`、`packages/frpc` 各自实现。
- **一个 frpc 进程注册多个代理**：一份配置声明多个 `http` / `tcp` 代理，共用一条 WS 连接。
- **一期运维**：结构化日志 + systemd 服务文件。Web dashboard 的归属见待决分支（用户已表达想要，形态未定）。

## 理由

- 协议定义放 shared 包，避免两端类型漂移——这是自研协议最容易踩的坑。
- 一进程多代理贴近官方 frp 的使用心智，连接数少、配置集中。
- 结构化日志足够排查当前规模的问题；systemd 保证开机自启和崩溃拉起。

## 后果

- pnpm monorepo 需要 workspace 配置，构建链路比单包复杂一点。
- 一进程多代理意味着单个 frpc 崩溃会同时影响它承载的所有代理——可接受，但配置里要能分组。
- Web dashboard 会带来管理面（谁有权限改配置、配置存哪），这是一个新设计分支，不能悄悄塞进一期。
