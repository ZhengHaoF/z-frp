# ADR-0003: 控制与数据走单条 WebSocket，streamId 多路复用

- 状态：已接受
- 日期：2026-11-16

## 背景

frpc 与 frps 之间需要传两类东西：控制信令（注册服务、心跳、错误）和业务数据（HTTP/TCP 请求与响应）。两种架构：

- 控制通道与数据通道分离（类似官方 frp 的多连接模型）
- 单条连接上用 stream ID 多路复用

## 决策

用一条长期存活的 WebSocket 连接，控制信令和业务数据都跑在上面，用 `streamId` 区分不同流。

## 理由

- 只需一个端口（443），防火墙与安全组配置最简单。
- WebSocket 天然支持双向、保活、浏览器可调试，Node 生态有成熟库（ws）。
- 当前规模小，单连接的吞吐足够；先把功能闭环跑通优先。
- 便于让 frps 完全隐藏在 Caddy 后面（见 ADR-0004）。

## 后果

- 单条弱网连接上所有流同生共死：连接断开时该连接上的所有 stream 都要重建。需要定义重连与会话恢复语义（见待决项）。
- 头部开销与帧序由自己保证，需要设计简单可靠的帧格式（类型、streamId、payload、结束标志）。
- 存在队头阻塞风险：一个慢消费者可能拖慢同一连接上的其他流，需要背压设计（见待决项）。
- 预留演进：若将来吞吐不够，可在保持对外行为不变的前提下把数据面换成独立通道（ADR-0002 中提及的"先简单后优化"）。
