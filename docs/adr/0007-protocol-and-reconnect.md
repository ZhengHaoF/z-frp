# ADR-0007: 帧格式与断线重连

- 状态：已接受
- 日期：2026-11-16

## 背景

WS 单通道上要传控制信令（注册、心跳、错误）和业务数据（HTTP/TCP 的请求响应），需要定帧格式；断线后流如何处理也要定。

## 决策

- **帧分层**：控制帧用 JSON（可读、易调试），数据帧用 binary（不浪费带宽）。共用同一套 `type` + `streamId` 信封。
- **断线**：frpc 检测到 WS 断开后自动重连，重连成功后把本地所有代理**全量重新注册**；不做流级会话恢复，断线期间活跃连接直接失败。

## 理由

- JSON 控制帧排查问题时直接看日志就懂，binary 数据帧避免 base64 的 33% 膨胀（数据库场景重要）。
- 全量重注册实现简单可靠；会话恢复要在两端缓存未确认数据、按 streamId 续传，复杂度高一个量级，当前规模不值得。

## 后果

- 控制帧解析要做 JSON  schema 校验，防止畸形消息打崩进程。
- 全量重注册意味着重连瞬间会有注册风暴，frps 需要对同一客户端的重注册做幂等（覆盖旧路由而非叠加）。
- 活跃 TCP 连接（如正在查库）遇到断线会直接断开，用户需要重连数据库——这是已知且接受的行为，要写进文档。
