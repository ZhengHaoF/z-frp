# ADR-0013: 客户端核心用 Rust 重写，界面用 Tauri

- 状态：已接受
- 日期：2026-11-17

## 背景

二期的客户端是「一条命令 + 一长串 key」，命令行体验尚可，但要发给不熟命令行的人，就得手把手教他打开终端、cd 到目录、粘贴 key、别关窗口。目标是"填 key 点一下就能用"，同时别把已有协议搞坏。

评估过三条路：

1. **本地 Web 控制台**（Node 起一个本地网页）：最快，但等于用户还是要先 `node xxx.js` 才能看到网页，鸡生蛋问题没解决。
2. **Tauri + 复用 Node 客户端**：界面有了，但打包进去的 Node 运行时几十 MB，还要管理子进程与 IPC，长期维护成本高。
3. **Tauri + Rust 重写客户端核心**：没有 Node 运行时，单 exe 十几 MB，进程内直接调用核心；代价是要把协议用 Rust 再实现一遍。

选 3。协议本身很小（1 种数据帧 + 14 种控制帧），且服务端是现成的，可以用"字节对拍"把兼容性钉死。

## 决策

- 新增 Cargo workspace：`crates/frpc-core`（协议、连接状态机、HTTP/TCP 转发）、`crates/frpc-cli`（bin `zfrpc`）、`apps/desktop`（Tauri 壳 + 静态前端）。
- **服务端（Node frps）不动**。frps 只认协议不认语言，Rust 客户端必须与 Node 客户端字节兼容。
- 兼容性用三层测试保证：Node 导出字节向量 → Rust 断言逐字节相同；同一条测试隧道用两个客户端跑同样请求比对；复用现有 fixture 做端到端。
- Node 客户端 `packages/frpc` **保留**，作为回退与对照实现，不删除。
- 桌面端只做**一个连接卡片**：key + 服务端地址 + 状态 + 日志。不做隧道列表——key 唯一对应一条隧道，配置由服务端 `config-push` 下发。
- 前端不用打包器：`src/index.html + styles.css + main.js` 直接作为 `frontendDist`，改样式不用起 dev server。

## 理由

- 用户要的是"双击打开、填 key、点连接"，只有进程内的原生壳能做到。
- 客户端逻辑本来就不复杂，重写的成本低于长期维护"打包 Node 运行时 + 子进程 IPC"。
- 服务和客户端解耦后，两边可以独立演进；协议不改，服务端一行不用动。

## 后果

- 上线前必须跑通字节对拍，否则会出现"能连上但传输出错"的玄学问题。实测在对拍阶段就抓到 `remotePort` 被序列化成 `remote_port` 的字段映射 bug。
- 服务端也暴露了一个老 bug：HTTP 入口把整个请求体塞进一个数据帧，>64KB 时抛错并**带崩 frps 进程**。修在服务端（`sendData` 自动分片 + 入口兜底 catch），两个客户端都受益。
- Node 客户端与 Rust 客户端并存，文档需明确推荐顺序（Rust/桌面端优先，Node 回退）。
- 桌面端 key 明文存 `app_config_dir/settings.json`，与"key 等价于隧道通行证"的既有定位一致，不再额外加密。
